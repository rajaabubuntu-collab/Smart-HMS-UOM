## Revised implementation sequence

1. **Public website and glass design foundation (this revision).** Public `/`, meaningful links, demo disclosure, login/register and shared workspace styling; mobile, keyboard, reduced-motion, reduced-transparency and offline-API checks. Keep the existing booking and clinical workflows usable.
2. **Sri Lankan hospital settings and identity.** Admin-only audited configuration and a deliberately small public projection; verified brand/address/reception number/hours, Colombo time, LKR, +94 validation and opt-in communication preferences. Provider secrets stay in server configuration, never public settings. Confirm whether Sinhala/Tamil are now in scope; translate real content and validation together if adopted.
3. **Socket.IO and doctor dashboard.** Authenticate using the existing session; enforce origin and server-assigned per-user/per-doctor rooms; disconnect expired/revoked/deactivated sessions. Emit only after committed mutations. Send minimal invalidation events, fetch authorised state through REST, reconcile after reconnect, keep bounded polling. Test cross-role/other-patient isolation and logout while connected.
4. **Charts.** Add Recharts for daily appointments/status, completed consultations, revenue receipts/reversals, department activity and ratings. Use server-side date-range aggregates, Sri Lanka day boundaries, LKR units, empty/loading/error states and tabular equivalents. Reconcile totals with the existing reports; label activity counts without claiming bed/capacity utilisation.
5. **Email, SMS and account recovery.** Provider adapters, transactional delivery outbox, per-event/channel deduplication, bounded retries/backoff, delivery attempts/statuses and redacted logs. Start with local/sandbox delivery; choose a Sri Lanka-capable SMS provider and verified sender. Distinguish queued, accepted and delivered. Keep diagnoses/prescriptions out of SMS/email; link to the authenticated portal. Implement AUTH-006 on top of verified email delivery. Live sends need configured credentials and explicit test recipients.
6. **Remaining administration and SRS gaps.** Patient activation, department maintenance, IP audit requirement, doctor timeline and list pagination. Clarify retention/deletion and configuration permissions with the project supervisor.
7. **Report and acceptance evidence.** Update diagram sources, architecture, sequence diagrams and user manual. Run measurable performance/usability/browser checks, then return to deployment and automated backups.

## Diagram corrections and report edits

Three diagram occurrences were visually inspected: Figure 3.8 (p.24), Figure C.2 (p.40) and SRS Figure B.2 (p.92). Figures 3.8/C.2 already include audit review and feedback review, and do not show an external AI actor. The older Figure B.2 differs from them and is narrow/rasterised and difficult to read. It depicts the built-in “AI System” as an external actor and includes a long unclear dependency. An internal rule engine belongs inside the system boundary. “Get department guidance” may include “Evaluate symptom rules”; it must not imply an external AI provider or clinical diagnosis.

Use separate legible views for public/patient, care team and administration. Add the public visitor, password recovery, notifications, rescheduling, prescription revision, payment recording/reversal, feedback review, audit review and hospital settings. Model email/SMS gateways as external supporting actors only in the target view. Socket.IO and Recharts are implementation mechanisms, not actors or human goals. An SMTP service should not appear to be implemented before delivery exists.

The companion [use-case specification](use-cases.md) distinguishes current capabilities from planned ones and supplies an editable UML source. Reconcile all three occurrences in the main design chapter, Appendix C and SRS Appendix B when revising the report; they currently present inconsistent models.

The runtime defaults to an eight-hour session (`server/src/config.js`), while NFR-S03 states a 24-hour default and Appendix C leaves expiry open. Record the eight-hour implementation decision for supervisor review. AUTH-009/NFR-S05 also need explicit public-route exceptions for registration, login, recovery and any deliberately published hospital directory; protected clinical routes must remain authenticated.

Preserve the historical interim statement that implementation had not started. In the final report or a dated addendum, replace future-tense technology claims with evidence: React 19, native fetch, plain CSS, Zod and Node's test runner/Playwright are the current choices; Tailwind, Axios, express-validator and Jest from Table 3.3 were not adopted. Socket.IO/Recharts are still planned. Explain these substitutions instead of claiming those libraries are installed.

Keep the original exclusions (no laboratory equipment, insurance integration, native mobile app or telemedicine). New public-facing hospital content must not fabricate clinicians, awards, success rates, emergency facilities, opening hours or contact details.

## Design direction and technical references

Use a cool pearl/blue background, translucent navigation, rounded controls, fine highlights and gentle shadows. Keep tables, forms, medication details and allergy warnings on readable surfaces. Provide a persistent “Solid surfaces” preference plus system preference fallbacks. This is a web interpretation, not native Apple Liquid Glass rendering. Apple's guidance separates material/navigation from underlying content and accounts for reduced transparency and increased contrast: [Apple materials guidance](https://developer.apple.com/design/human-interface-guidelines/materials).

Socket.IO defaults to at-most-once arrival and recovery can fail, so durable application state and reconnect refresh are part of the plan: [delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/) and [connection state recovery](https://socket.io/docs/v4/connection-state-recovery/).
